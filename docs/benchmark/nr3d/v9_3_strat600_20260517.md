# NR3D v9.3 strat600 — first canonical small-batch run on UI-overhaul + keyframe-selector fix

This is the **first benchmark-grade evaluation** on the new canonical pilot fold
`v9_3_strat600` (600 stratified samples, calibrated to ±0.19 pp of full filtered
7805 on the v9.1_fix reference). It runs the v9.3 HEAD which adds:

1. The root-cause fix for the `runtime.keyframe_selector is None` regression
   (commit `32bfd0e`, `BaseStage2Runtime.__init__` fail-loud + `build_selector_tools`
   safety net) — so `select_by_text` actually parses queries instead of
   silently returning ERROR.
2. The BEV on-demand-labels + tighter-crop UI overhaul (commit `2cd5e6d`),
   including the new `view_bev(categories=[...])` argument.
3. The `mark_frame_with_bbox` unified top-left + colour-matched label redesign
   (commit `7696625`).
4. The `_v93` cache-bust tag on highlight-overlay BEV filenames (commit `ae83fea`).

The headline conclusion is **statistically equivalent to v9.2 text-first FULL**:
strat600 places it within ±2 pp of v9.2 text-first FULL on every column, well
inside the strat600 ±2.3 pp 90 % band on Overall.

## What changed since v9.2 (code-level deltas with commit hashes)

| Commit | Change |
|---|---|
| `32bfd0e` | **Root-cause fix** for `runtime.keyframe_selector is None`: `BaseStage2Runtime.__init__` raises `ValueError` if `enable_stage1_text_retrieval=True` without a selector; `build_selector_tools` drops `select_by_text` if selector is `None`; production call sites updated to either pass selector or explicitly disable text retrieval. |
| `2cd5e6d` | BEV `SceneBEVConfig`: tighter `crop_margin` (8→3), `crop_white_threshold` (250→245); label defaults sharper (font scale 0.85→1.0, thickness 2→3, outline extra); `label_all_when_highlight_is_none=False` (clean default); `_overlay_proposal_labels` rewritten for selective labelling. |
| `7696625` | `mark_frame_with_bbox._draw_label` redesigned: DUPLEX font, ~20 % larger, always top-left inside bbox (fallback above), background = bbox stroke colour, text colour auto-picked by luminance for contrast. |
| `ae83fea` | `_render_highlighted_bev` cache filename embeds `_v93` renderer-version tag so future renderer changes auto-invalidate stale overlays. |

The strat600 fold itself was added in `cdca81f` (one commit before the v9.3 fix
chain).

## Caveats

- **Calibration is on v9.1_fix only.** The strat600 fold was salt-tuned so
  the v9.1_fix subset metrics ≈ v9.1_fix full metrics on the 5 leaderboard
  columns. It does *not* guarantee a different agent's subset metrics ≈ its
  own full metrics by the same margin. For v9.3, treat ±2.3 pp 90 % as the
  Overall variance budget, with wider bands per-tier (Easy ±2.9 pp, Hard ±3.5
  pp, V-Dep ±4.5 pp, V-Indep ±2.7 pp). The +5.24 pp Hard delta vs v9.2 text-
  first FULL is **just outside** the per-tier band, so it's a soft positive
  signal that needs a FULL re-run to confirm.

- **No FULL 7805 run on v9.3 yet.** This is the first calibrated small-batch
  run on the v9.3 HEAD; a true v9.3 FULL run is the next step if you want to
  pin down the +5 pp Hard / +3 pp V-Indep signals.

- **ModelHub 429s present but absorbed** — 1 418 retryable 429 events in the
  log, all consumed by the AK rotator. No timeouts; no AK exhaustion.

- **1 / 600 sample "failed" status** — this is `scene0578_00::18::13314`
  where the agent submitted `selected_object_id=None` (graceful no-match,
  the query is OOD: "small black box on the right side attached to the
  wall" — the wall outlet is not a catalog proposal). The runner records
  `status=failed` because no integer pid was emitted; the NR3D leaderboard
  scores this as `is_correct=false`, which is correct.

- **`tool_trace` for 1 sample contains `None` entries** when the deep
  agent loop hit a transient framework error and the runner skipped trace
  serialization for that step. The `selected_object_id` was still emitted
  correctly. Counts above are computed only over `dict`-typed trace entries.

- **bbox metrics are not directly comparable across runs of different
  proposal pools** — v9.3 uses the same `pack_nr3d_v9_catalog_first` pool
  as v9.2 and v9.1_fix, so Acc@0.25 / 0.50 / mean IoU are comparable within
  the v9.x family. The 66.83 % Acc@0.25 on bbox ≈ 66.67 % classification acc
  is expected since the catalog assigns one 9DoF box per proposal — bbox
  IoU degenerates to "did you pick the right proposal_id".
