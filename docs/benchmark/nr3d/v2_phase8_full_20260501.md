The distribution is bi-modal (60 % at 1.0, ~21 % at 0.0). This is the
expected GT-pool signature: when the agent picks the right candidate, IoU is
~1.0 (because the candidate IS the GT instance); otherwise it picks a wrong
instance whose oriented box rarely overlaps the GT.

### How to read the Ours-vs-published gap

This v2 table is historical and should not be quoted as the leaderboard row.
The public leaderboard reports target-instance classification accuracy, while
v2 reported 9-DoF IoU on the GT object pool. Under the GT pool, IoU@0.50
collapses to "picked the correct object id", so v2 was an accurate proxy for
classification on the unfiltered 8584Q fold. v3 later made that explicit and
added the canonical `mentions_target_class=True` filter and official slices.

The current protocol summary is [protocol.md](protocol.md). The short version:
the old target-type-only-pool concern was wrong; the real non-comparability of
v2 is metric/reporting format, not a different candidate-pool family.

## Bug Fixes During Run

Two changes to `src/evaluation/scripts/` were made mid-run after diagnosing
real-data crashes; both are committed alongside this doc:

1. **`prepare_pack_v1_inputs_nr3d.py`**: skip Phase 8 objects with empty `class_name` from the proposal pool. One bg-leakage object found in scene0496_00 (`is_background=1, class_name=[], num_detections=0`) was crashing pack-prep. Fix preserves object_id space (no renumbering); skipped object retains bbox via the loader if it's ever a target. NR3D test never targets this id.
2. **`run_nr3d_vg_side_by_side.py`**: wrap per-sample exceptions into a `failed` sentinel so a single rotten sample (e.g. an upstream image-500 surviving all retries) does not collapse the whole `executor.map` and kill the run. The sentinel records `iou=0`, `status=failed`, and the error string; the sample still counts toward the headline `n` and Acc@*. Companion test updated:`test_compare_backends_persists_failed_sentinel_on_sample_exception`.

## Throughput Notes

The run spanned a ~14h period during which upstream API throughput varied
significantly:

- Early phase (02:00–11:00): ~3–5 finishes/min (3 keys saturated, normal contention)
- Mid burst (06:01): ~30 transport timeouts in 30 sec, all attempt 1/5 self-heal, no escalations
- Trial windows (14:10–14:22): tested workers=40 and workers=48
  - 48 workers → 1.17/min, escalation to attempt 3/5 within 8 min → **rolled back**
  - 40 workers → 5.0/min steady-state (same as 32) → **rolled back** (no upside)
  - Conclusion: 32 is the local optimum given the 3-key bandwidth; more keys is the only real lever
- Late phase (14:50–18:37): ~19–23 finishes/min (upstream capacity recovered for unknown reason); this stretch contributed the bulk of the completions

Total transport failures across the run: 197, of which 22 escalated past
attempt 1/5; **0** ever exhausted attempt 5/5 (i.e. the client retry loop
absorbed all transient failures).

## Caveats

- **GT-pool inflation**: every aggregation instance is a candidate. Fraction at IoU=1.0 reflects "agent picked the right instance ID", not bbox regression quality. Detector-pool variant is the next experiment.
- **Per-LLM-call durability gap**: `tool_calls` and `llm_calls` tables in `runs.sqlite` are still empty for this run. Same gap as v1 smoke; the NR3D ingester does not yet read the runner's per-sample agent trace into per-tool / per-call rows. Tracked in CLAUDE.md "Per-LLM-call durability".
- **Easy/Hard, View-dep/View-indep splits not reported**: NR3D's per-utterance `is_view_dep` / `is_hard` flags are on the loader sample but the side-by-side runner does not aggregate by them. Worth adding for the next version.
- **Failed sentinels (3.34 %) are real losses**: 287 samples scored 0 because of upstream rejection or agent malformed output. They are NOT excluded from the headline; the true "given a successful prediction" Acc would be slightly higher (~80.4 % when filtered).
