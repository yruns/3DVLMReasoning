# NR3D v9.3 strat600 catalog-only A/B — does dropping `select_by_text` recover 83 %?

This is the **Layer-1 catalog-only experiment** asked for in the v9.3 strat600
post-mortem: same fold, same code, same guards, same workers, same wall-time
budget — **only** `--disable-stage1-text-retrieval` changes between this run
and the `v9_3_strat600_20260517` run it pairs with.

The motivating hypothesis: if v9.1_fix scored 82.95 % by accidentally running
catalog-only (because the `select_by_text` wrapper bug forced fall-through),
then making catalog-only **the policy** should recover the 83 %.

**Result: No.** Clean catalog-only on v9.3 gives **64.17 %** on strat600 —
basically identical to v9.2 no-text FULL (64.65 %), and **−18.78 pp below
v9.1_fix FULL**. The 83 % was *not* a clean catalog-only policy; it was an
artifact of (broken `select_by_text` + text-first playbook + agent's
learnt fall-through). v9.4 needs a different strategy.

## Why "clean catalog-only" ≠ "v9.1_fix's 83 %"

v9.1_fix was *not* a clean policy. It was a **bug-state**:

1. `Stage2DeepAgentConfig.enable_stage1_text_retrieval = True` (i.e., the
   text-first playbook was loaded, the text-first system prompt was
   served, and `select_by_text` was advertised as the primary entry).
2. The `select_by_text` tool was **registered** (because the config said
   so) but **broken** at the wrapper-bypass layer — every invocation
   returned `ERROR: runtime.keyframe_selector is None; cannot run
   Stage-1 text retrieval`.
3. The agent learned, within each sample, to invoke `select_by_text`
   once (per the text-first playbook's "first move" advice), receive
   the ERROR, and **fall through** to `list_scene_proposals` /
   `select_by_proposal` / etc.

That fall-through path, **combined with the text-first playbook prose**
("if select_by_text fails, switch to `select_by_proposal` / `select_by_region`
on candidate IDs you can read from the BEV + inventory"), produced a
qualitatively different agent than either:

- Today's clean text-first (v9.3 strat600 `66.67 %`), where Stage-1 actually
  works and returns useful (sometimes misleading) frames.
- Today's clean no-text (v9.3 strat600 `64.17 %`, this run), where the
  agent is *told* to start with the catalog, not "start with
  select_by_text and recover from failure".

**The catalog-only-by-accident state seems to dominate both clean
policies by ~18 pp.** That's a large enough gap that it can't all be
fold variance (strat600 90 % band on Overall is ±2.3 pp). The remaining
~16 pp must come from one of:

- (a) Some aspect of the **text-first playbook prose** that helps even when
  `select_by_text` ERRORs out (e.g., the "first move = scout, then
  refine" framing biasing the agent toward more careful disambiguation).
- (b) Some aspect of the broken-Stage-1 ERROR turn that **anchors** the
  agent — burning one turn on a guaranteed-ERROR call may pace the
  reasoning cadence differently from the chassis seeding catalogue first.
- (c) Some interaction with the chassis's image-injection / evidence
  budget that benefits from a "no Stage-1 frames in the first turn"
  contract that the bug provided for free.

Disentangling these requires a per-sample trace audit on a matched batch
(N ≥ 30) sliced by what move the agent makes after `load_skill`. See
"Next steps" below.

Same policy (`enable_stage1_text_retrieval=False`), only differences are

Overall delta is **−0.48 pp**, which is well inside the strat600 90 % band
(±2.3 pp on Overall). This confirms two things at once:

1. **strat600 is a faithful proxy for FULL on the no-text policy too** —
   the fold calibration that was done against v9.1_fix doesn't degrade
   when applied to a different policy.
2. **v9.3's UI overhaul + selector fix doesn't change the no-text
   ceiling** — same policy, same backend, same playbooks → same ~64 %.
   This is a clean negative result for "v9.3 changes lift catalog-only".

## What's next (concrete v9.4 plan after this negative result)

Layer 1 alone doesn't recover 83 %. The remaining ~16 pp gap forces a
different strategy than the post-mortem proposed. Three avenues, in
recommended order:

1. **Audit the v9.1_fix fall-through behaviour on this fold (30 min).**
   Pick 30 strat600 samples and run them at HEAD `d5f40ba` (the
   wrapper-bypass-bug worktree from `v9_1_fix_FULL_REPRO`). Compare
   per-turn traces against the v9.3 text-first run on the same 30 ids.
   The question is: after the broken `select_by_text` ERROR, does the
   agent make systematically *better* second moves than today's
   `select_by_proposal`-first agent? If yes, what does it do differently?
   This is the cheapest way to isolate the ~16 pp.

2. **Force the bug-state policy on v9.3 (15 min, 1 line):**
   construct a v9.4-trial agent with `enable_stage1_text_retrieval=True`
   but pass `keyframe_selector=None` and bypass the construction guard
   in a one-off launcher. The tool would return ERROR on every call,
   exactly like the v9.1_fix bug. If this recovers 80+, then the
   behavior is entirely about the text-first playbook prose + forced
   fall-through, and v9.4 should re-introduce that pattern *cleanly*
   (e.g., a `force_first_move_to_text=True` flag that emits ERROR
   intentionally without calling Stage-1).

3. **Per-query routing (v9.4 proper, ~1 day):**
   In `chassis_tools.load_skill` or in `Stage2DeepResearchAgent.run`,
   inspect the query tokens and pick the playbook variant per sample:
   tokens ∩ `{front, behind, back, right, left, facing, leftmost, rightmost, looking, across}` ≠ ∅
   → load `_no_text` variant (view-dep heuristic); else → load text-first
   variant. Already justified by the audit doc. Run on strat600.

The other option (do nothing, ship v9.3 as the new baseline) leaves
~16 pp on the table vs the v9.1_fix bug-state high-water mark. We
should not ship until we either explain the gap or close it.
