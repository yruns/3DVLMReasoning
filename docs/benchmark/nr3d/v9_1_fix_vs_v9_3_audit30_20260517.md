# v9.1_fix vs v9.3 audit on 30 strat600 samples — what is the 16 pp made of?

This is **Step 1** of the v9.3 post-mortem (see
[v9_3_strat600_notext_20260517.md §What's next](v9_3_strat600_notext_20260517.md)):
run `v9.1_fix` (broken-Stage-1 worktree at commit `d5f40ba`) and `v9.3`
(both text-first and no-text variants) on the **same** 30 stratified
strat600 samples, then audit per-sample tool traces.

The question this audit answers: where does v9.1_fix's ~16 pp lead over
clean v9.3 policies come from, if not from "Stage-1 actually working"?

**Answer**: It comes from a **deliberation cadence** that the broken
`select_by_text → ERROR` + the text-first playbook prose accidentally
enforce. v9.3 (both clean variants) cuts the cadence short and commits
to wrong answers earlier.

## The 6 "magic" cases — what does v9.1_fix do differently?

Pulled from per-sample `tool_trace`. Pattern: every magic case starts
with `select_by_text → ERROR`, then a systematic catalogue walk, then a
**re-mark + re-submit** cycle triggered by the evidence-frame guard.

| Sample | Query | v9.1_fix trace shape | v9.3-txt trace shape |
|---|---|---|---|
| `scene0015_00::47` | "longer whiteboard … furthest from the doorway" (Easy V-Ind) | `select_by_text→ERR / view_bev / inspect 40 + 47 / mark 40+47 / inspect each / mark each separately / submit 40 (wrong) / mark 47 / submit 47 ✓` | `view_bev / inspect 40+47 / mark f0(47) / select(40) / mark(40) / submit 40 ✗` |
| `scene0086_00::10` | "stall door to the disabled bathroom" (Easy V-Ind) | `select_by_text→ERR / list / view_bev / inspect 10+29 / select(10) / select(29) / mark f44(10) / mark f53(29) / crops / submit 10 ✓` | `inspect 10, 29 / view_bev / select_proposal(10,29,1,28) / inspect / select / mark(28) ... 27 tools, ends submit 29 ✗` |
| `scene0231_00::45` | "picture on the wall near the kitchen" (Hard V-Ind) | `select_by_text→ERR / list / view_bev / inspect 16+20+45 / select(16,20) then select(45) / mark f131(45) / submit 45 ✓` | `view_bev / select_text x2 / select_proposal(many) / inspect 16+20+45 / mark f42(16,20) / submit 20 ✗` |
| `scene0338_00::21` | "facing the boxes, the box in the back on the left side" (Hard V-Dep) | `select_by_text→ERR / view_bev / list / select(0,18,19,20) / mark f0 / submit 21 / re-mark f53 / submit 19 / submit 21 ✓` | `list / view_bev / select(0,18,19,20) / mark f1 / inspect each / submit 21 / submit 19 ✗ (stays wrong)` |
| `scene0648_00::10` | "plant closest to the mirror" (Easy V-Ind) | `select_by_text→ERR / list / retrieve_object_context / view_bev / list / select(9,10) / inspect each / list_frame / mark f21 / view_bev / mark f21 again / submit 10 ✓` | `list / select(9,10) / view_bev / list_frame / inspect each / mark f21 / select / compare_spatial / mark / submit 10 first / submit 9 ✗` |
| `scene0697_00::7` | "nightstand with the blue striped snake in front of it" (Easy V-Dep) | `select_by_text→ERR / inspect 6+7+22 / view_bev / select(6,22) / select(7) / mark f73(7) / mark f0(6,22) / crops × 2 / submit 6 ✗ first / mark f78(7) / submit 7 ✓` | `select_text / select(6,7) / view_bev / mark f0(6,7,22) / select_frame_neighbor / mark f3(6,22) / submit 6 ✗` |

The recurring v9.1_fix pattern:

1. **Burn one turn on `select_by_text → ERR`.** This is "wasted" but
   *anchors* the agent into the text-first playbook's documented
   fall-back chain.
2. **Read the whole catalog**: `view_bev`, `list_scene_proposals`,
   `inspect_proposal` on every plausible candidate.
3. **Mark each candidate in its OWN best frame**: not one shared frame
   with all candidates, but `mark_frame_with_bbox(f=A, ids=[X])` and
   `mark_frame_with_bbox(f=B, ids=[Y])` separately.
4. **Initial submit, then evidence-frame guard fires** → re-mark on a
   *different* frame → re-submit (often with a corrected proposal id).
5. The "first submit was wrong, second submit was right" outcome occurs
   in 3 / 6 magic cases (`scene0015_00`, `scene0338_00`, `scene0697_00`).

The v9.3 versions skip steps 3-5 (per-candidate marking + corrective
re-submit) and commit early on the wrong proposal. This is the cadence
gap.

## Counter-cases — what does v9.3 do that v9.1_fix gets wrong?

Two cases where v9.3-txt (and v9.3-no) win against v9.1_fix:

| Sample | What v9.1_fix did wrong | What v9.3 did right |
|---|---|---|
| `scene0153_00::18` "rail beside the door, larger towel on it" | 17 tools, 2 submits, both for `pid=15` (wrong). Two `select_by_proposal` calls between submits didn't change the pick. | v9.3-txt: 22 tools, included **compare_proposals_spatial** + targeted re-mark `f24(17)` between marks — landed on `pid=18` correctly. |
| `scene0616_00::30` "painting next to a window, on the right side of the door" | 22 tools, `mark_frame_with_bbox(f=0, ids=[29,30,3,28])`, first submit `30` (correct!) then re-mark and re-submit `29` (wrong) — evidence-frame guard misfired here. | v9.3-txt: 25 tools, picked `30` first and didn't re-submit incorrectly. |

So the cadence is not always a win. In `scene0616_00` the re-mark
cycle that helps v9.1_fix on 6 cases actively hurts here: the
evidence-frame guard's "look at one more frame" advice led to a
*degraded* spatial inference. This is consistent with the audit doc's
note that Stage-1 is "either great or hopeless" — the same applies to
the cadence, except more subtly.

## Aggregate tool stats on the 30 ids

| Stat | v9.1_fix | v9.3-txt | v9.3-no |
|---|---:|---:|---:|
| `select_by_text` calls | **30 (100 % ERR)** | 11 (2 ERR) | 0 |
| Avg tools/sample | **16.1** | 15.6 | 13.8 |
| Avg `submit_final`/sample | 2.20 | 2.27 | 2.23 |
| `inspect_proposal`/sample | 3.07 | 3.07 | 3.07 |
| `mark_frame_with_bbox`/sample | **2.90** | 2.73 | 2.13 |

Key insight: **`inspect_proposal` rate is identical** across all three
runs at 3.07 / sample. The big differentiator is
**`mark_frame_with_bbox`** — v9.1_fix marks 36 % more frames than
v9.3-no and 6 % more than v9.3-txt. The text-first playbook's mention
of "if select_by_text fails, switch to … then `mark_frame_with_bbox`"
appears to be driving the extra marking pass on v9.1_fix. Stripping
that prose in v9.3-no is what costs the marks.

The `submit_final` rate (2.20-2.27) is essentially identical, but
**when** the submits happen and **what evidence preceded each submit**
differ. That's the cadence.

## What this means for v9.4

Three concrete next experiments, in increasing implementation cost:

### Experiment A — "Force the bug-state on v9.3 cleanly" (1 LoC, ~30 min total)

Add a config flag `Stage2DeepAgentConfig.force_stage1_text_retrieval_to_error: bool = False`.
When True, `select_by_text` is **registered** (text-first playbook +
system prompt unchanged) but the tool body short-circuits to:
```python
return "ERROR: forced Stage-1 disable (v9.4 cadence experiment)"
```
without touching `KeyframeSelector` at all. Run on strat600. If this
recovers 80+ %, the entire ~16 pp gap is from the cadence, and v9.4
should ship this flag (and probably default it on for NR3D).

### Experiment B — "Stronger playbook prose" (~2 h)

If A doesn't recover the full 16 pp, edit
`scene_exploration_playbook.md` to force the bug-state cadence
explicitly:
- "First move: always make exactly ONE `select_by_text` call. Treat
  any response (including ERROR) as data and proceed to step 2."
- "Step 2: enumerate via `view_bev` + `list_scene_proposals` + 1
  `inspect_proposal` per shortlisted candidate."
- "Step 3: `mark_frame_with_bbox` ONCE PER candidate in its
  best-visible frame (not a shared frame)."
- "Step 4: `submit_final`. Step 5 (auto via evidence-frame guard):
  if blocked, re-mark on a different frame and re-submit."

This is the "clean replica of the cadence" approach. Costs more
prompt tokens.

### Experiment C — "Per-query routing + cadence-forced playbook" (~1 day)

Combine the v9.4 routing plan (text-first playbook for rare-target /
OOD queries, `_no_text` for view-dep) with the explicit cadence
playbook from Experiment B. This is the highest-investment
experiment but addresses both findings (Stage-1 working hurts on
view-dep + cadence helps on the rest).

## Caveats

- n=30 has ±15 pp 90 %-band on Overall — absolute numbers should be
  read qualitatively. The ~13 pp gap between v9.1_fix and v9.3-txt on
  this fold matches the 16-pp full-fold gap within that band.
- The cadence hypothesis is supported by 6 magic cases + tool-rate
  aggregate stats, but `n=6` is small for any single mechanistic claim.
  Run Experiment A above on full strat600 (600 ids) to confirm.
- The evidence-frame guard plays a key role in the magic cases (forces
  the re-mark cycle). v9.3 also has this guard enabled — the difference
  is whether the agent reaches the re-mark stage with the right
  alternative in mind.
