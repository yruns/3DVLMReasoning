## Project Overview

3DVLMReasoning is a two-stage framework for 3D scene understanding. Stage 1
selects visual evidence from 3D scene assets, and Stage 2 runs a DeepAgents /
LangChain VLM agent over benchmark-specific task packs. The active work is the
EmbodiedScan Visual Grounding pack: prepare candidate 3D bbox proposals, render
visible marked keyframes, and ask the Stage 2 agent to select the proposal that
matches the referring expression.

The important design point for the next Linux agent: **proposal generation must
be provider-pluggable**. Keep the current GT proposal pool as an oracle/debug
upper bound, add V-DETR full-scene ScanNet detection as the first real detector
provider, and leave the schema open for future providers such as ConceptGraph,
UniDet3D, BIP3D-derived proposals, or mask-fitted geometry.

## Potential Problems

- **Problem**: It is tempting to overwrite `pack_v1` with V-DETR outputs.
  - **Impact**: The GT oracle baseline disappears and future comparisons lose
    their upper-bound control.
  - **Suggested Fix**: Keep `pack_v1` or rename it to `pack_gt`; create
    `pack_vdetr` separately. Add `source` to every output artifact.

- **Problem**: `run-detector` writes feasibility `ProposalRecord` JSONL, but
  Stage 2 expects `vg_proposal_pool` derived from `proposals.jsonl`,
  `visibility.json`, and rendered annotated frames.
  - **Impact**: Stage 2 may run with missing tools or wrong visibility.
  - **Suggested Fix**: Add the explicit conversion script described above.

- **Problem**: V-DETR full-scene proposals are scene-level. Multiple VG samples
  in the same scene must reuse the same detector proposal file.
  - **Impact**: Running detection per target wastes GPU and can make proposal
    IDs inconsistent across samples.
  - **Suggested Fix**: Assign stable proposal IDs per scene after sorting by
    score. Reuse the scene pack for all target IDs in that scene.

- **Problem**: The current `prepare_pack_v1_inputs.py` docstring says no
  detector is involved.
  - **Impact**: Future agents may think V-DETR was intentionally removed.
  - **Suggested Fix**: Keep that statement only for the GT provider path.
    Add a new detector-provider prep script or rename docs to make provider
    boundaries explicit.

- **Problem**: V-DETR boxes are AABB in our export (`aabb_from_vdetr_corners`)
  after converting corners. EmbodiedScan GT is 9-DoF.
  - **Impact**: Acc@0.50 may be lower for rotated or thin objects.
  - **Suggested Fix**: Preserve raw V-DETR corners in metadata and later add
    OBB fitting if needed. For the first integration, AABB 9-DoF with zero
    Euler angles is acceptable and already tested in feasibility code.
