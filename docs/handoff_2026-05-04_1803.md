## 1. Project context

This repository (`/Users/bytedance/project/3DVLMReasoning`) is a
two-stage 3D scene understanding framework:

- **Stage 1** (`src/query_scene/`): query-driven keyframe retrieval
  from a 3D scene graph. Returns 1-3 RGB frames as visual evidence.
- **Stage 2** (`src/agents/`): a VLM agent (gpt-5.4-2026-03-05 via
  internal ModelHub) built on LangChain + DeepAgents. Receives the
  Stage 1 keyframes, can call back into Stage 1 (`request_more_views`,
  `request_crops`, `switch_or_expand_hypothesis`), and submits a
  proposal_id from the Mask3D pool.

The current branch (`feat/scanrefer-v3-query-driven`) iterates the
ScanRefer visual-grounding benchmark under the Camp-A zero-shot setup
(Mask3D pool detection-mode, no GT view oracle, 3D IoU evaluation
against ScanNet aggregation-derived bbox).

The frozen development fold is **random100** (seed=20260503), 100
utterances × 66 scenes, regenerable via
`scripts/build_scanrefer_random100_fold.py`. Per the user's
methodology rule (memory: `feedback_iterate_on_100_random_first.md`):
**iterate on random100 only; do not push to full 9508-val until the
fold metric is clearly improving.**

The v2 GT-view-oracle baseline (67.0/59.0 on random100, 69.92/62.79
on full val) is a controlled upper bound — it picks initial keyframes
by GT `target_id` Phase 8 visibility, which leaks the answer location
to the agent. v3.x removes that oracle and is the apples-to-apples
zero-shot path.

### 4.4 [SURFACED] Two reasoning meta-bugs Codex missed (Claude2 only)

**Meta-bug 1: agent ignores its own deterministic tool's verdict.**

In `scene0149_00::2::3` ("kitchen cabinet next to the stove. it is
between the wall and the stove."), the agent ran:

```
compare_proposals_spatial(
    candidate_ids=[2, 3, 12, 14, 27, 33, 36, 43],
    anchor_id=10 [stove],
    relation='closest_to'
) → ranked_ids=[33, 14, 43, 27, 36, 12, 3, 2]
```

The agent then **submitted proposal 19**, which is not even in
`ranked_ids`. The agent override silently — no contradiction surfaced
to the runtime. Across the 44 samples this pattern shows in 1 direct
case + 1 indirect case via `scene0660_00::4::4` (anchor = candidate
itself).

**Meta-bug 2: inverse-anchor selection on pair queries.**

In `scene0660_00::4::4` ("a black leather arm chair. next to another
same chair."), the query is symmetric: find a *pair* of black-leather
chairs adjacent to each other, then pick one. The agent locked
`proposal 3` as anchor and asked
`compare_proposals_spatial(anchor_id=3, relation='closest_to')`.
This is the inverse of the symmetric pair search the query implies.
GT 4 was 0.27 m below GT 3 vertically and fell outside any
distance ranking from 3. The agent never evaluated 4.

These are NOT in the closed-set rubric but are real, evidenced, and
addressable. They motivate two independent fix proposals (TADG, ADC)
described in § 6.

## 5. Stage 1 Keyframe selection: full investigation record

### 5.1 What Stage 1 keyframe selection actually does today

Code path: `src/evaluation/scripts/prepare_pack_v1_inputs_scanrefer.py`
→ `_select_keyframes()` dispatch by `--keyframe-mode`.

Three modes exist:

| Mode | Path | Status |
|---|---|---|
| `gt_target` | `select_keyframes_from_phase8_target(target_id)` — top-5 frames where GT target_id is most visible (Phase 8 GT visibility) | v1/v2 oracle path. **Leaks GT.** Not for zero-shot. |
| `query_driven` | `KeyframeSelector.select_keyframes_v2(query, k=3)` — Phase 8 hypothesis-parser via `query_scene/keyframe_selector.py` + `query_scene/query_parser.py` | v3 path. 38% fallback rate to Mask3D-density top-3. |
| `mask3d_query_driven` | parse query → categories → score frames by sum of Mask3D-CG visibility weights of same-category candidates → top-3 (X1 patch) | v3.1+ path. 0% fallback. |

Both `query_driven` and `mask3d_query_driven` use a `QueryParser`
(LLM-based) to parse the natural-language description into a
`HypothesisOutputV1` structure (`src/query_scene/query_structures.py`).
The parser returns 1-3 ordered hypotheses, each with a target
category list + spatial constraints + anchors.

After parsing, the two modes diverge:

- `query_driven` looks up which Phase 8 GT objects in the scene
  match the parsed categories, then picks frames where those objects
  are visible. Failure mode: parser guesses a category not in scene
  (38% of random100 — fallback to Mask3D-density top-3).
- `mask3d_query_driven` matches parsed categories against Mask3D-CG
  proposal labels via fuzzy token overlap (`_matching_proposal_ids`
  in `prepare_pack_v1_inputs_scanrefer.py`), then picks frames where
  those Mask3D candidates are visible. Failure mode: 0% (always
  finds at least one match thanks to fuzzy + Mask3D vocab being
  ScanNet200).

### 5.2 Funnel-level evidence: keyframe selection is NOT the lever

Funnel report on v3.3 (`tmp/v3p3_funnel_report.json`):

```
F1=100  F2=65  F3=83  F4=86  F4b=94  F5a=42  F5b=14
```

35% of samples start with initial KFs that don't show the GT target.
But **callbacks recover 21pp of those (F4 reaches 86%)**. The
remaining 14% are unrecoverable through callbacks — but only 14pp
are actually lost to keyframe coverage.

The 44pp gap from F4=86 to F5a=42 is **picking-stage** loss, and
70-73% of that is not picker error but Mask3D label noise (§ 4.3).

**Therefore: do not iterate on Stage 1 keyframe selection.** The
infrastructure for callbacks is solid, the initial-KF source choice
doesn't matter much, and the bottleneck has moved upstream into
proposal labeling.

### 5.3 Parser correctness — open question, not yet measured

The funnel does NOT verify "did the parser correctly identify the
target category from the description?". Today it uses
`target_category` from the pack-prep input, which equals ScanRefer's
`object_name` (a weak GT leak via the annotation file).

This means we cannot distinguish:

- "Parser got the right category but Mask3D mislabelled the GT bbox"
  (the dominant failure per § 4.3)
- "Parser got the wrong category (so Mask3D label is irrelevant)"
  (might be a non-trivial chunk of mask3d_label_mismatch; both
  workers' rubrics couldn't tell because they trust `object_name`)

**Open task** (§ 6.5 below): add an F0 stage to the funnel that runs
the LLM parser fresh on each query and measures parser-target ↔
GT-target category match.

### 5.4 Stage 2 ↔ Stage 1 callback loop — confirmed working

The v3.2 commit (`a2ab5c7`) fixed several runtime correctness bugs
that previously made the iterative ReAct loop a no-op:

- `submit_final` defer: now waits for pending images to be injected
  before accepting the agent's final answer
- stride=1 vs saved-stride mismatch (was producing 107
  path-resolve warnings per random100 run)
- raw `*-rgb.png` vs `*-rgb.jpg` path resolution
- structured `proposal_id` payload extraction via `vg_proposal_pool`
- per-sample `tool_trace` durability into SQLite

After v3.2, `tool_calls` durability is real (1855-2116 rows per
random100 run; see § 3 SQLite table). The agent is making 18-21
tool calls per sample on average and going to turn ≥ 2 in many
cases (vs 0% before v3.2). The iterative loop is functional.

### 5.5 Cumulative keyframe coverage (F4) is high enough — picking is the bottleneck

Proven again by the audit (§ 4.3):

```
86 samples (out of 100) had GT target visible in some frame the agent saw
  └── 42 picked correctly
  └── 44 picked wrong  ← of which 70-73% are Mask3D label noise (unreachable)
14 samples had GT target NOT visible after all callbacks
  └── unrecoverable on this fold under current pipeline
```

The 14 F4-fail samples are the only place where keyframe-selection
or callback improvements have headroom. They are < 14pp of fold-level
movement. Mask3D label noise is 30+ samples × ~50% conversion = 15+
pp of headroom. CVRA dominates by ~3×.

### 6.1 [P0] CVRA — CLIP-Visible Retrieval Augmentation

**Source**: Claude2 audit, § 5.1 of `tmp/picking_error_audit_v3p3_claude.md`.
Cross-validated against Codex's "Visible-Proposal Candidate Sweep"
(same root cause, different control surface).

**Bucket**: `mask3d_label_mismatch` (32 samples on this fold,
70-73% of picking errors).

**Mechanism**: at the proposal-discovery layer (the body of
`find_proposals_by_category` in `src/agents/packs/vg_embodiedscan/tools.py`),
augment label-based retrieval with CLIP-text-similarity ranking over
proposals visible in the agent's cumulative keyframe set.

```python
def find_proposals_by_category_v2(category, runtime):
    label_hits = [p.id for p in ctx.proposals
                  if p.category.strip().lower() == category.strip().lower()]
    visible_ids = visible_in_cumulative_keyframes(runtime)
    text_emb = clip_encode_text(category)        # cache per category string
    visible_only = [p for p in ctx.proposals
                    if p.id in visible_ids and p.id not in label_hits]
    scored = [(p, clip_score(text_emb, runtime.crops[p.id])) for p in visible_only]
    scored.sort(key=lambda x: -x[1])
    augmented = [p.id for (p, s) in scored if s >= TAU][:K_AUG]
    return {"label_hits": label_hits, "clip_visible_aug": augmented,
            "available_categories": [...]}
```

Calibrate `TAU ≈ 0.21` cosine, `K_AUG ≤ 5` on a 20-sample held-out
slice. Tag augmented ids in metadata (`source: 'clip_visible'`) so
the agent can apply slightly higher caution.

Differentiation from Codex's unbounded "Visible-Sweep": **bounded
top-K** (≤5) avoids the v3.4 distractor-flooding failure mode. Label
priority is preserved — augmented set is appended, not replacing.

**Expected affected samples** (per Claude2 § 5.1 sub-bucket
breakdown):
- 24 wildly-unrelated GT labels (`monitor`/desk, `book`/window,
  `paper bag`/kitchen cabinet, `armchair`/trash can, etc.) — CLIP-text
  should win these because the visual crop genuinely depicts the
  query category
- 4 generic GT labels (`object`, `mat`, `shoe`) — easy wins
- 4 adjacent GT labels (`monitor` for a desk dominated by a monitor;
  S38 inverse case where GT monitor is labelled `desk`) — hard cases
  for CLIP-rerank, conservative 50% win rate

Conservative estimate: **18-24 of 32 flip F5a → Yes**, i.e. random100
Acc@0.25 lifts from 48 → 56-60, Acc@0.50 lifts from 42 → 48-52.

**Falsifiable validation**:

1. Implement CVRA behind feature flag `agent.use_clip_visible_aug = True`.
2. Run on the same v3.3 random100 pack: same-fold A/B vs v3.3.
3. Run `scripts/evaluate_keyframe_funnel.py` with the new audit
   field `clip_visible_aug_included_gt_overlap: bool` per sample.
4. **PASS criterion**: ≥ 16 of 32 mask3d_label_mismatch samples
   flip F5a → Yes; ZERO new F5a regressions on the 56 non-mismatch
   samples.
5. **STRETCH criterion**: random100 Acc@0.25 ≥ 56, Acc@0.50 ≥ 48.
6. **Disaggregation requirement**: the version doc must include a
   per-sample table with GT label, query category, CLIP score of

### 6.2 [P1] TADG — Tool-Answer Disagreement Gate

**Source**: Claude2 audit, § 5.3 of `tmp/picking_error_audit_v3p3_claude.md`.
Codex did not propose this — it surfaced via Claude2's deeper
walkthrough of `scene0149_00::2::3`.

**Bucket**: meta-bug 4.4 (agent ignores its own
`compare_proposals_spatial` verdict at submit time). 1 direct case
(S6) + 1 indirect case (S39 inverse-anchor) on this fold; defensive
elsewhere.

**Mechanism**: add a runtime gate in the agent's `submit_final`
handler. The gate tracks the most recent
`compare_proposals_spatial` call whose `relation` argument matches
a relation token in the parsed query. If `submit_final.proposal_id`
is NOT `ranked_ids[0]` from that call (and the call is recent —
last 8 tool calls), the gate returns a **soft block**:

```
"Spatial-tool ranked X first for relation R; you are submitting Y.
 Provide a tool_override_reason or revise."
```

The agent can either re-submit with `tool_override_reason: <text>`
populated (which logs the explicit divergence) or revise its pick.
No reasoning capability is removed — divergence is forced to be
explicit.

**Expected affected samples**:
- S6 direct hit: `compare_proposals_spatial(closest_to, anchor=stove)
  → ranked_ids=[33, 14, 43, 27, 36, 12, 3, 2]`; agent submitted 19.
  TADG soft-blocks → agent revises (predicted F5a flip).
- S39 indirect hit: agent's anchor=3 with relation=closest_to
  returned `[9, 1, 5]`; agent submitted 3 (the anchor itself).
  TADG soft-blocks because rank-1 (9) ≠ submitted (3). Predicted
  partial win.
- S33: agent's `compare_proposals_spatial` returned `[4, 2, 3]`
  ranked first = 4, agent picked 4. TADG passes (no false block).

Total: **1 direct win + 1 indirect win** + defensive elsewhere.

**Falsifiable validation**:

1. Implement TADG behind feature flag.
2. Re-run the 3-sample subset {S6, S26, S39}; verify TADG
   triggers on S6 and S39 only.
3. **PASS criterion**: TADG triggers on ≥ 2 of the targeted
   samples; ≥ 1 sample flips F5a → Yes.
4. **Trigger-rate sanity**: on full random100, TADG must
   trigger on ≤ 5% of samples. > 20% means the gate is too
   aggressive — tighten relation-token matching.
5. **New audit fields**: `tadg_triggered: bool`,
   `tool_override_reason: str | null`. Persist via the existing
   `tool_trace` durability.

**Risk and detection**:
- *Stale-ranking blocks*: restrict memory to last 8 tool calls.
  Symptom: trigger rate spikes when tool_trace length grows.
- *Multiple-relation queries*: gate must check all parsed
  relations, not just the latest. Symptom: agents over-submit
  `tool_override_reason: "different relation"` (> 30% of overrides).
- *Soft-block stuck loops*: count repeated identical-override
  events; auto-escalate to hard error after 3 retries.

**Files to touch**:
- `src/agents/runtime/deepagents_agent.py` and
  `src/agents/stage2_deep_agent.py` — gate logic in submit-final path
- query parser to extract relation tokens (already partially
  supported via `HypothesisOutputV1.spatial_constraints`)
- `src/agents/skills/chassis_tools.py` (if needed to wrap
  `submit_final` body) — TBD
- tests in `src/agents/tests/test_stage2_deep_agent.py`

**Estimated wall time**: 2-3 h implementation + 1 h smoke. ~half day.

**Independent of CVRA** — both can be measured in the same run.

### 6.3 [P2] CFOA — Camera-Frame Ordinal Axis Tool

**Source**: Claude2 audit, § 5.2. Codex's "Row-Order Disambiguation
Tool" addresses the same bucket with similar but coarser approach;
Claude2's version is recommended for camera-frame inference + axis
return.

**Bucket**: `ordinal_or_row_directional` (5 samples on this fold,
11-14% of picking errors).

**Mechanism**: new VG-pack tool

```python
compare_proposals_along_axis(
    candidate_ids: list[int],
    axis_term: str,          # 'left' / 'right' / 'front' / 'back' /
                             # 'near_wall' / 'far_wall' / 'nearest_to_camera' / ...
    row_clustering: bool = True,
) → {ordered_ids, row_membership, axis_value, axis_vector_world_frame}
```

Body:

1. Resolve `axis_term` to a 3-vector in world frame using current
   keyframe poses (mean of forward/right/up across the keyframes
   the VLM is currently looking at). Viewpoint-independent terms
   (`near_wall` / `far_wall`) fall back to scene-bbox-extreme axes.
2. Project each candidate's centroid onto that axis.
3. If `row_clustering=True` and perpendicular spread exceeds
   row-height threshold, run DBSCAN on the perpendicular component
   to assign `row_index` (auto-scaled to scene bbox).
4. Return ordered ids + per-id row_index + axis_value + the
   resolved `axis_vector_world_frame` (so agent can sanity-check
   the interpretation).

Differentiation from Codex's Row-Order: camera-frame inference
(more aligned with natural-language "right" than scene-x); explicit
axis-vector return for debug; row-clustering coupled with axis
projection in one call.

**Expected affected samples** (Claude2 per-sample table):

| Sample | Query | CFOA call | Outcome |
|---|---|---|---|
| S2 | "left side faces the window" | axis='left' | Partial — needs orientation tool |
| S14 | "far end of the table" | axis='far_from(camera)' on table axis | Direct win |
| S18 | "fourth from the right and second row" | axis='right', row_clustering=True | Direct win |
| S24 | "third from the right wall, eight of them" | axis='right_wall' | Direct win |
| S32 | "first chair on the left side of the table" | axis='left' along table edge | Direct win |

Conservative count: **4 of 5 flip F5a → Yes**.

**Falsifiable validation**:

1. Implement CFOA behind feature flag, register in
   `vg-grounding-playbook` (so `list_skills` surfaces it).
2. Re-run the 5 sample_ids; verify the tool is invoked at least
   once per sample.
3. **PASS criterion**: ≥ 3 of 5 flip F5a → Yes.
4. **Axis-stability sanity**: two independent runs of the same
   sample must produce `axis_vector_world_frame` within 30°.
   Larger drift = viewpoint inference unstable.
5. **Non-degradation**: tool-call rate on the 30
   mask3d_label_mismatch samples must be < 5% (tool only used
   on ordinal queries).

**Risk and detection**:
- *Reference-frame ambiguity*: speaker's "right" ≠ camera's
  "right" in some scenes. Tool exposes resolved axis to agent for
  detection; auto-flip is out of scope.
- *Row clustering brittleness*: DBSCAN epsilon auto-scaled but
  can fail on dense seating. Falsifier: row_index swap between
  runs → downgrade to "indicative only".
- *Tool misuse*: agent may overuse on non-ordinal queries.
  Mitigated by playbook gate + non-degradation check.

**Files to touch**:
- `src/agents/packs/vg_embodiedscan/tools.py` — new tool
- `src/agents/packs/vg_embodiedscan/skills/vg_spatial_disambiguation.md` — usage docs
- `src/agents/packs/vg_embodiedscan/skills/vg_grounding_playbook.md` — decision tree
- tests + walkthrough doc

**Estimated wall time**: 1 day. Wait for CVRA + TADG to settle

### 6.4 [P3] ADC — Anchor-Disambiguation Constraint for Same-Category Pair Queries

**Source**: Claude2 audit, § 5.4. Targets meta-bug 4.4 (inverse
anchor on "X next to another X" pair queries). Codex did not
propose.

**Bucket**: 1 fold sample direct (S39); out-of-fold extrapolation
is the actual motivation (5-10% of full-val ScanRefer queries are
pair-form ≈ 100-200 picks on full 9508).

**Mechanism**:

(a) Playbook update in `vg-spatial-disambiguation`: when the parser
sees a self-referential pair pattern (`X next to another X`,
`X near a same-category X`, `X beside the other X`), the playbook
forbids using any same-category proposal as `anchor_id` in
`compare_proposals_spatial`. Valid path is to enumerate
same-category proposal pairs and rank pairs by visual / attribute
match.

(b) Optional new tool

```python
find_proposal_pairs(
    category: str,
    max_pairwise_distance: float,
    attribute_constraint: str | None = None,
) → list[(id_a, id_b, score)]
```

returns same-category proposal pairs whose centroids are within
`max_pairwise_distance`, optionally filtered by
attribute_constraint via CLIP-text-image score, ranked by
`inverse_distance × attribute_match`.

For "X next to another same X" queries, agent's loop becomes:
parse → detect pair pattern → call `find_proposal_pairs(category)`
→ optional `request_crops` for top pair → submit member with
better attribute match.

**Expected affected samples**:
- S39 direct hit: routes agent to
  `find_proposal_pairs('chair', max_pairwise_distance=1.0)`
  which returns pairs (3, 4), (3, 9), (9, 4).
  Attribute-CLIP("black leather arm chair") rerank disambiguates.
- Out-of-fold: 100-200 picks on full 9508 (rough estimate).

Conservative for this fold: **1 sample (S39)**. Out-of-fold
is the motivation.

**Falsifiable validation**:

1. Implement ADC: parser pattern detector + (optional) tool +
   playbook update.
2. Targeted rerun on S39: verify trace contains
   `find_proposal_pairs` call (or refrains from
   `compare_proposals_spatial(anchor_id=<chair>)`).
3. PASS: F5a flips on S39.
4. **Pattern-detection precision** ≥ 0.9 on hand-labeled
   50-query held-out set. Symptom of over-trigger:
   regressions on `is_unique=True` cases.

**Risk and detection**:
- *Pattern false positives*: "the chair to the left of *the* chair"
  (definite article) is ambiguous. Symptom: out-of-fold
  regressions on `is_unique=True`. Detection: per-version
  ADC-on vs ADC-off Acc@0.25 on Unique slice.
- *find_proposal_pairs blowup*: 26-chair scene → C(26, 2) = 325
  pairs. Cap at top-K by inverse-distance.
- *Attribute-string handling*: ScanRefer attribute language is
  noisy. Threshold conservatively.

**Files to touch**:
- query parser to detect pair patterns
- `src/agents/packs/vg_embodiedscan/tools.py` (optional new tool)
- `src/agents/packs/vg_embodiedscan/skills/vg_spatial_disambiguation.md`

### 6.5 [P0 diagnostic] Add F0 stage to the funnel: parser-fidelity check

**Source**: § 5.3 above. The funnel today trusts ScanRefer's
`object_name` field as the GT category, which is a weak GT leak.
We cannot distinguish "parser correct + Mask3D wrong" from "parser
wrong" within the `mask3d_label_mismatch` bucket.

**Mechanism**: extend `scripts/evaluate_keyframe_funnel.py` with
an optional `--run-parser` flag. When enabled, for each sample:

1. Run `query_scene.query_parser.QueryParser.parse(query)` fresh
2. Collect the parser's target categories
   (`hypothesis.grounding_query.root.categories` from rank-1
   hypothesis)
3. Compare to GT category via fuzzy match (`_category_match` in
   pack-prep)
4. Emit boolean `F0_parser_target_matches_gt_category`

With F0 we can split `mask3d_label_mismatch` into:
- F0=Yes & F4=Yes & F5a=No: pure Mask3D label noise (CVRA's target)
- F0=No & F4=Yes & F5a=No: parser-layer error (different fix path)

**Expected effort**: 1-2 h (parser already cached per scene; just
add the comparison + audit field).

**Why P0 even though it's a diagnostic**: this changes the expected
CVRA gain. If parser-error overlap with mask3d_label_mismatch is
> 20%, CVRA's effective ceiling is 24/32 → 19/32, not the
estimated 18-24. CVRA's PASS criterion (§ 6.1.4) needs to be set
accordingly.

**Cost**: parsing 100 queries × ~3-5 s × gemini-2.5-pro pool ≈
5-8 min of LLM time per funnel run. Cache to a JSON sidecar so
re-runs are free.
